# Alder Home reload performance

11 November 2026. Scope: Home launch, return from another screen, and catalog tab changes. This review uses the source code and public documentation. It has no TV timing data.

## What Alder does today

- `MainActivity.showPage()` reads the saved Stremio library and add-on list while it requests fresh copies. Catalog pages also reuse answers held in memory or saved to disk. `Http` stores the last responses, and `Images` keeps decoded bitmaps in separate card and backdrop caches. The HTTP response cache can also reuse artwork across process restarts when the server's cache policy permits it.
- `Screen.background()` uses a shared six-worker executor for cache reads and blocking requests. A local read on a tab switch can queue behind slow work from the previous tab. Generation checks suppress old callbacks, but queued work can still run. `showPage()` clears rows before replacements arrive. An add-on list change can also call `showPage(quick = false)`, which bypasses saved answers on that rebuild.
- Normal return from a title or playback already refreshes in the background. Catalog updates defer replacing a focused row. The library restores focus by card tag when the title still exists. These are behaviors to preserve.
- On the first Continue Watching render, an item with `timeOffset == 1` can trigger a saved metadata lookup on the UI thread. If saved add-ons are unavailable, the fallback can call `Stremio.addons()` there. Cache setup also trims saved responses during the first `Screen.onCreate()`. Trace those paths to learn how much startup time they cost.

## Recommended order

1. **Keep the current page usable during refresh.** Leave visible rows and focus in place while fetching. Apply changed results when ready and preserve focus by title ID when that title is still present. A slow or failed request should leave the last good rows usable. On a tab switch, show the destination's cached row when available. On a cache miss, show a lightweight row placeholder and keep tab navigation and Back available. [Android offline-first guidance](https://developer.android.com/topic/architecture/data-layer/offline-first) · [Android TV navigation](https://developer.android.com/training/tv/get-started/navigation#provide-clear-focus-and-selection)
2. **Give the first row its own path to cached data.** Read and prepare the saved library or first catalog row off the UI thread without waiting behind network refreshes. Move the Continue Watching metadata check off the UI thread while preserving its episode release filter. Reuse the current cache first. If traces show that parsing full responses still delays the first row, persist a small per-profile snapshot of the first row. Treat it as display data and keep watch progress reconciliation in the library code.
3. **Give visible content priority.** Draw real card titles and focus first, request the visible posters and focused artwork next, then load later rows and optional metadata. Alder already sizes images and prefetches nearby art. Try a small cached backdrop first only if the trace shows full-size artwork is a significant part of the blank interval. Google's public Street View API documents thumbnails and multiple tile resolutions. The analogous choice for Alder is to prioritize the detail needed in the current viewport. [Street View tile documentation](https://developers.google.com/maps/documentation/tile/streetview)

## How to verify

Compare cold launch with and without saved data, return from playback, and tab switches while slow catalog requests are active. On slow or unavailable Wi-Fi, verify that cached content can still take focus and that a late refresh does not move focus unexpectedly. Record time to first frame, first visible actionable card, and first useful artwork separately. Use Android's TTID and TTFD for app launches and measure from the remote action to actionable focus for in-app changes. Trace cache queue time, JSON parsing, row construction, and image decode before choosing the next optimization. [Android startup timing](https://developer.android.com/topic/performance/issues/launch-time) · [Macrobenchmark metrics](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics#startuptimingmetric)
